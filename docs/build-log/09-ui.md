## The ideas worth knowing

**1. Derived state lives in ONE place.** The Brain knows 4 states; the face shows 11 (it also needs
the connection, an open confirmation, the running tool, tasks, mute). If every window worked that out
itself, the companion and the main window could disagree. So main computes `Presence` with a pure
function (`faceFor`, first matching rule wins: offline > needs you > reconnecting > tool > muted >
brain > tasks > idle) and pushes it only when it changes. Windows just draw it. Same idea as a Redux
selector, or a database view: one definition, everyone reads the result.

**2. The timeline lives in main, not in the page.** Reload or reopen the window and the session is
still there: it comes in the snapshot. Each change is pushed as ONE event; an event whose id the page
already has *replaces* it (a card goes running → done; a line of speech grows). That's an upsert, like
`INSERT … ON CONFLICT(id) DO UPDATE`. Speech fragments are glued into lines in main (same speaker,
nothing in between, < 10 s apart).

**3. Ordering on one pipe.** The page subscribes first, then asks for the snapshot. A push that
arrives *before* the snapshot's reply is older than the snapshot (pushes and replies share one ordered
IPC pipe, and main sent that push before it took the snapshot), so the page drops it. Pushes after
the reply are newer and apply on top. (First version wrongly replayed early pushes on top, which
would have rolled state back.)

**4. Each request has a context.** `{ id, source, tainted }`, created when a request starts. A click on
Undo/Cancel in our UI gets its OWN context (`source: 'ui'`), so it can't reset the spoken request's
caution mode or exactly-once id. And it goes through the same `runTool` path as the AI: checked,
confirmed if needed, written to the Ledger. The UI never has a back door.

**5. No "Allow" button in the page.** The rail shows what's waiting, but answering is only possible
in the native Windows dialog or by voice. Any script in our page could click a page button; nothing
in the page can click a Windows dialog.

**6. A window that's only partly there.** The companion window is 260 × 176 and transparent; only the
112 px face should catch the mouse. `setIgnoreMouseEvents(true, { forward: true })` makes the window
click-through but still forwards mouse *moves*, so the page can hit-test the body and say "pointer
over the face", and main switches clicks back on. Drag = the page sends screen-space deltas; main
moves the window, then snaps the face to the nearest edge.

**7. A real Windows bug, found by measuring.** On a 150% display, `setPosition` on a transparent
window grew it 1–2 px per move (260 → 281 after two drags). `setBounds` with the size every time
fixes it. Found because the test read the window's bounds after each drag, not because it looked wrong.

**8. One microphone owner.** `voice-glow` can open the mic itself; we don't let it. It gets a level
*getter* from our Ear/Mouth. Two capture streams would double CPU and could fight over the device.
Same for the faces and the mic meter: levels are read per frame through refs, never put in React
state (60 re-renders a second for nothing).

**9. Canvas at device pixel ratio.** A canvas is a bitmap: 112 CSS px on a 150% screen needs 168
real pixels, or it's blurry. Every face/glyph canvas sizes its bitmap to `cssSize × devicePixelRatio`
and scales the drawing.

**10. Supply chain.** `voice-glow` and `thinking-orbs` are weeks old with one maintainer. Before
installing: `npm pack` → read the files → no install scripts, no network calls, no eval, no
dependencies. Pinned exact versions. Listed in `docs/disclosure.md`.

## Performance fix (same day): "it's slowing my laptop"
Arnav: the new UI made the laptop lag. Measured, not guessed (scratch `measure.ps1`: same fake mic of
quiet room noise for every build, 15 s with the window open, 15 s hidden in the tray; CPU per process
from process times over a stopwatch-timed window, GPU from Windows' `GPU Engine` counters for our PIDs):

| Idle | CPU (of one core) | GPU engines | RAM |
|---|---|---|---|
| Before the UI (627b1b2): open / hidden | 46% / 69% | 3% / 7% | 395 MB |
| UI round 1 (d2a22e2): open / hidden | 145% / 172% | 48% / 66% | 682 / 731 MB |
| **After the fix: open / hidden** | **30% / 23%** | **2.5% / 1.4%** | **369 / 363 MB** |

Causes (from CPU profiles of each page):
- **Nothing ever slept.** We turned `backgroundThrottling` off (so the voice works from the tray), and
  that also means Chromium never pauses a hidden page AND `document.hidden` is always false. So every
  animation ran forever. Fix: main tells the page when its window is shown/hidden (`windowVisible`),
  and every loop sleeps while hidden.
- **voice-glow repainted every frame** (canvas + CSS clip paths) even with no voice. Now `paused` unless
  someone is speaking (+1.5 s so it fades instead of freezing).
- **The edge-glow loop (M1) ran 60×/s forever** in its hidden full-screen window. Now it stops once settled
  and wakes on a new level/state.
- **The faces used requestAnimationFrame always**, skipping frames. Waking 60×/s to do nothing still
  costs. Now: rAF only while moving; a 15 fps timer at rest; 4 fps when still; nothing when hidden.
- Smaller: the mic meter (20/s timer, DOM touched only on change), the once-a-second heartbeat (ignored
  while hidden, it re-rendered the page), a hidden companion is destroyed instead of hidden.
- **Wake word noise gate** (`main/wake/gate.ts`, tested): the speech model only runs around sound; the
  0.3 s before sound is replayed so "Hey" isn't clipped. Checked with the recorded "Hey Dreamwalker,
  what time is it?" clip: woke both times, full question heard.

Lessons: measure every build the same way, against a baseline; and an "off" switch for throttling
means YOU are now responsible for sleeping.

## Same evening: window screenshots, saved sessions, and the rest of the lag
**Screenshot ONE window** ("what's in this Chrome tab?"): `take_screenshot` takes an optional `window`.
- Matching uses Windows' capture list, which has EVERY visible window by title (the program list we use
  elsewhere has only one "main window" per program, so a second Chrome window was invisible to it).
- Capture uses `PrintWindow(…, PW_RENDERFULLCONTENT)`: the window draws itself into a bitmap, which works
  for GPU-drawn windows and windows behind others. Electron's own window capture returned an EMPTY picture
  for a visible, normal window, and the first version then told Gemini the window was "minimised": a
  false claim. Now "minimised" is only said when Windows confirms it (`IsIconic`).
- Speed: 9.7 s → ~1.7–2.2 s (compile the C# helper once into a DLL; ask Electron for window names only).
- Verified by having one test copy capture ANOTHER test copy (never the user's windows), and looking at
  the picture.

**Sessions are saved** (`%APPDATA%\dreamwalker\sessions\<start>.json`, this computer only) and picked up
again after a restart within 2 h (the same window in which Gemini still remembers the conversation).
**Copy** in the Session header puts the whole conversation on the clipboard as text. Entries that were
still running when the app stopped come back as "interrupted", never as "running" forever (found from
Arnav's screenshot: a card stuck on running…, because the app was killed inside the 2 s save delay).

**Why the laptop still lagged "in between"** (evidence, not guesses):
1. `npm run dev` used `--watch`: every save of a main-process file restarted the running app (save at
   20:07:33 → new process at 20:07:34). A restart = Electron + 3 windows + the wake-word model + a new
   Gemini connection, and it cut off the conversation. Dozens of saves today = dozens of restarts.
   `dev` no longer watches; `dev:watch` keeps the old behaviour.
2. My own testing on the same machine (test copies, builds, perf-counter sampling).
3. The animation bug above (fixed).
4. Small, always-on: the terminal, two Claude Code sessions, OMEN Hub, the audio engine, Wallpaper Engine.
Ruled out: heat (51 °C), power mode (Unleashed), memory (no paging), disk, drivers (DPC 0.4%). An early
"CPU stuck at half speed" reading was wrong: the test ran in a hidden background process, and Windows 11
deliberately runs those slower to save power.

## Questions

2. The page drops pushes that arrive before the snapshot reply. Why is that safe, and why would
   replaying them be wrong?
3. Why does an Undo click get its own request context instead of using the current one?
4. Why is there no Allow button in the "Waiting on you" card?
5. How does a transparent window let clicks through but still know when the mouse is over the face?
